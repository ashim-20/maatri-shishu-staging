# Implemented API

[openapi.json](openapi.json) is the OpenAPI 3.1 contract generated by `npm run api:docs` from the current domain schemas. This is a same-origin workspace API implemented with Next.js route handlers and Supabase PostgreSQL RPCs.

| Endpoint | Purpose |
|---|---|
| `POST /api/auth/login` | Supabase password login for an active, provisioned staff profile |
| `POST /api/auth/logout` | Revoke the current Supabase session; active staff status is not required to log out |
| `GET /api/workspace` | Full scoped profile, record snapshot, recent audit and server time |
| `POST /api/sync` | One operation or an atomic group of 1–30 operations |
| `POST /api/audit` | Durable, idempotent profile-read/print metadata |
| `GET /api/export` | Audited JSON export for health workers and supervisors |

In local demo mode these protected server APIs return unavailable; the browser uses its synthetic Dexie workspace. The login endpoint issues project-specific Supabase SSR cookies with HttpOnly and SameSite=Lax, plus Secure in production. Session refresh happens through the Next.js proxy. Browser JavaScript does not manage a Supabase bearer token.

Every POST requires `Origin` to match the application origin. The server derives account, role and facility from the validated session. An operator may not supply their own effective role/facility. Protected responses use `Cache-Control: private, no-store` and an `X-Request-Id` header.

## Commands, revisions and receipts

A create operation contains `id` (operation UUID), `entityId` (record UUID), `entityType`, `action`, the full `data` payload, `expectedVersion: 0`, `wardId` and `createdAt`. Updates retain the record ID, use a **new** operation ID and supply the version currently being edited. `batchId` groups a form locally. `approve_clinical` and `activate` are restricted schedule transitions; their data payload is empty.

```json
{
  "operations": [
    {
      "id": "60000000-0000-4000-8000-000000000001",
      "entityId": "60000000-0000-4000-8000-000000000002",
      "entityType": "pregnancies",
      "action": "create",
      "data": {
        "motherId": "60000000-0000-4000-8000-000000000003",
        "lmp": null,
        "edd": null,
        "dateSource": "unknown",
        "status": "active"
      },
      "expectedVersion": 0,
      "wardId": 3,
      "createdAt": "2026-11-04T06:00:00.000Z"
    }
  ]
}
```

The example is illustrative: its mother must already exist in the operator's scope. It must not be replayed against a live clinical project.

Order parents before children within a batch. The RPC commits the entire batch, revisions, audit entries and receipts in one transaction. A successful response is `{ "results": [{ "record": ..., "duplicate": false }] }`. An identical retry returns the stored result with `duplicate: true`. Each operation ID is scoped to the authenticated actor.

Reuse the **same operation ID and payload** after an uncertain network response. Changing payload under that ID returns a conflict. For a reviewed correction/rebase, create a new operation ID. Unknown/client-only envelope properties are stripped before the receipt is stored. The client never deletes queued operations before an acknowledgement.

Dates without times use Gregorian `YYYY-MM-DD`. Timestamps use ISO 8601 UTC; `births.time` and clinic start time are local `HH:mm` values. Calendar-month dose ages use month arithmetic, not a fixed number of days. A recorded/approximate date is not automatically verified.

## Authorization and errors

Zod checks input shape. PostgreSQL independently checks values, links, scopes, permissions and revisions. Direct authenticated table writes are denied. Immutable care, consent, verification, contact-attempt and birth history must be appended rather than overwritten. FCHV may record unverified vaccination history; only authorized health staff verify or record maternal clinical contacts.

| Status | Meaning / client action |
|---|---|
| 401 | Sign in again; retain unresolved local work |
| 403 | Origin, current role, active account or scope does not permit the request |
| 409 | Stale version, reused operation ID or duplicate identity; explicit review required |
| 413 | Request exceeds the command size limit |
| 422 | Invalid fields, dates, relationships, evidence or approval state |
| 429 | Auth service rate limit; back off before retrying |
| 503 | Configuration, demo mode or temporary service failure; retain pending data |

Errors use `{ "error": "human-readable safe message" }`. They do not echo clinical payloads. The request ID is a diagnostic reference, not an authorization token. Full production observability/correlation review remains pending.

## Audit and export

Access events contain `id`, `action` (`read` or `print`), `entityType` (`mothers` or `children`), `entityId` and `occurredAt`. Receipt replay is idempotent. The device time is stored as observation metadata; database receipt time is authoritative. No narrative/phone/name fields belong in an access event.

JSON export is `maatri-shishu/1` with `exportedAt` and scoped `records`. It excludes Auth secrets and requires health-worker/supervisor permission. It is an exit/reporting artifact, **not** a complete PostgreSQL/Auth/audit backup or an implemented import format.

The current snapshot API is not paginated. Incremental cursor pull, richer staff administration, mapped HMIS CSV, identity merges and transfers are tracked in the development checklist.
